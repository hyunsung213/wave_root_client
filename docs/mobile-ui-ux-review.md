# 싹키워 스마트폰 UI/UX 리뷰

- **검토일:** 2026-10-10
- **범위:** `rootClient`의 모바일 우선 레이아웃, 인증, 주요 화면 내비게이션, 세션 처리, 바텀시트, 데이터 로딩·오류 상태, PWA·오프라인 처리 및 접근성 관련 소스
- **검토 방식:** 1차 코드 정적 검토에 더해, 2026-10-10 Chromium 브라우저에서 실제 서비스 로그인, 페이지 탐색, 분양→상품 확인, 실시간 스트림, 수정된 로컬 프로덕션 빌드의 반응형/성장기록 이미지 캡처 흐름을 교차 검증했다.
- **주의:** 화면 낭독기, 실제 iOS/Android 기기, 색상 대비 수치와 터치 실측은 확인하지 않았다. 실기기 검증이 필요한 내용은 완료로 간주하지 않는다.

## 요약

앱은 모바일 사용을 중심으로 한 화면 틀과 하단 내비게이션을 갖추고 있으며, 터치 가능한 아이콘 버튼의 최소 크기, 하단 안전 영역, 로딩·오류·빈 상태 구분, 인증 보호, 시트의 Escape 및 포커스 복귀 등 좋은 기반이 있다. 반면, iOS 노치 영역의 상단 안전 영역 선언, 비활성 메뉴의 시맨틱, 모달 배경 접근 차단, 새로고침 제스처 피드백은 우선 보완을 권한다. 네트워크가 끊긴 경우 앱 기능 전체가 오프라인 동작하는 것은 아니며, 현재 서비스 워커는 제한적인 자산 캐시와 정적 오프라인 안내를 제공한다.

## 최신 브라우저 점검 결과 (2026-10-10)

### 교차검증 결과

- **운영 프론트 기준선:** 제공된 테스트 계정으로 로그인 성공. 홈·분양·기록·알림·마이페이지·프로필·가입 화면을 열었고, 390px 및 320px 폭에서 가로 넘침은 관찰되지 않았다. 운영 계정의 식물 8개 조회, 분양 상세 시트→상품 확인 화면 이동, 결제 미구현 상태 안내를 확인했다. 주문·회원·알림 상태를 변경하거나 기록을 저장하지 않았다.
- **운영 스트림:** 실시간 페이지에서 카메라 MJPEG 응답 `200`, `multipart/x-mixed-replace`, 이미지 프레임 `1280×720`, UI의 `LIVE` 상태를 확인했다. 페이지 진입 직후에는 연결 중으로 보일 수 있어 최종 검증은 로딩 완료 후 수행했다.
- **운영 센서:** 현재 센서 API는 `503`을 반환한다. 화면은 측정값을 임의로 표시하지 않고 재시도 안내를 보여준다. 이 요청에서 센서·ESP32 연동 수정은 하지 않았다.
- **수정된 로컬 프로덕션 빌드:** 320px/390px 폭 주요 보호 화면의 가로 넘침 없음, 브라우저 JavaScript 예외 없음. 성장기록 모달의 배경 `inert`, 설명 연결 및 현재 스트림 캡처→JPEG 미리보기까지 확인했다. 테스트 계정의 프로필 저장·비밀번호 변경·알림 읽음·성장기록 생성 및 식물 생성/삭제는 데이터 변경을 피하기 위해 실행하지 않았다.
- **자동화 검사:** ESLint, TypeScript, Next.js production build 통과. 배포 완료 후 동일한 로그인/페이지/스트림 검사를 재실행해 이 절을 갱신한다.

### 이번 수정에서 반영한 항목

- `viewportFit: "cover"`와 공통 상단 safe-area 여백, 본문 건너뛰기 링크를 추가했다.
- 식물이 없는 경우의 실시간 메뉴를 실제 disabled 버튼으로 표현했다.
- 바텀시트를 portal로 분리하고 배경 본문·메뉴를 `inert`/`aria-hidden` 처리했다. 제목·설명 관계, 키보드 포커스 이동/복귀, Escape 닫기, reduced-motion 대응을 유지했다.
- 기록·알림·프로필 로딩 상태를 보조기술에 알리고 skeleton 장식은 숨겼다. 알림의 읽음 여부를 텍스트·버튼 상태에 반영했다.
- 이름·전화번호 수정은 `PATCH /api/web/users/me`를 호출하고 반환된 사용자 정보로 화면 상태를 갱신하도록 했다. 이메일은 읽기 전용으로 안내한다.
- 실시간 성장기록에서 스트림 프레임을 서버 측 단일 JPEG로 받아 미리보기하고, 기록 제출 시 `image` 파일로 함께 첨부한다. URL은 query string 대신 same-origin POST JSON body로 전달하며, 허용된 백엔드 서명 스트림 경로만 읽고 8초/5MB 제한을 둔다.
- 센서 오류 버튼을 모바일에서 센서 카드와 겹치지 않도록 왼쪽 고정 폭 영역으로 옮겼다.
- 홈·기록·알림·마이페이지의 당겨서 새로고침에 동작 전/진행 상태를 추가하고, 내부 스크롤 목록이 최상단이 아닐 때는 새로고침 제스처가 간섭하지 않게 했다.

## 발견 사항 및 권장 조치

### P1 — 노치/상단 안전 영역 대응을 명시적으로 확인할 것

- **상태:** 코드 반영 완료. iOS Safari 및 standalone 실기기 검증은 필요하다.
- **근거:** 최초 검토 당시 `viewportFit: "cover"` 및 상단 inset이 없었다. 현재 `app/layout.tsx`와 `components/layout/PhoneFrame.tsx`에 반영했다.
- **영향:** edge-to-edge로 표시되는 iPhone/PWA 환경에서 상단 상태 표시줄·노치 근처의 콘텐츠 위치가 브라우저 기본 동작과 달라질 수 있다. 실제 기기에서 가려짐이 확인된 것은 아니므로 재현 검증이 필요하다.
- **권장:** 지원 대상 기기에서 브라우저 탭 모드와 standalone 모드를 모두 확인한다. edge-to-edge를 의도한다면 viewport-fit과 공통 상단 safe-area padding을 명시하고, 페이지별 상단 간격과 중복되지 않게 조정한다. 하단 내비게이션 inset도 같은 기기에서 재확인한다.

### P1 — 비활성 ‘실시간’ 메뉴를 실제 비활성 컨트롤로 표현할 것

- **상태:** 코드 반영 완료. 스크린리더 발화는 실기기 확인이 필요하다.
- **근거:** 최초 검토 당시 비대화형 `<span>`이었다. 현재 `components/layout/BottomNav.tsx`는 이유가 설명된 disabled 버튼을 렌더링한다.
- **영향:** 회색 스타일만으로 상태를 추론해야 하고, 스크린리더 사용자에게 “분양받은 식물이 없어 사용할 수 없음”이 메뉴 항목으로 일관되게 전달되지 않을 수 있다. `aria-label`은 비대화형 span에 붙어 있어 메뉴 내비게이션 컨트롤과 같은 경험을 보장하지 않는다.
- **권장:** 비활성 버튼으로 구현해 `disabled`와 이해하기 쉬운 이름/설명을 제공하거나, 메뉴에서 제외하고 별도 안내를 제공한다. 키보드 및 화면 낭독기에서 메뉴의 항목 수와 비활성 이유를 확인한다.

### P1 — 시트가 열렸을 때 배경 콘텐츠의 접근을 차단할 것

- **상태:** 코드 반영 및 브라우저 DOM 검증 완료. VoiceOver/TalkBack은 확인이 필요하다.
- **근거:** 최초 검토 당시 배경 접근 차단과 설명 연결이 없었다. 현재 `components/ui/BottomSheet.tsx`가 본문·하단 메뉴에 inert/aria-hidden을 적용하고 설명 ID를 연결한다.
- **영향:** 직접적인 Tab 순환은 기본 사례를 돕지만, 포커스가 외부로 이동하는 상황이나 스크린리더의 가상 탐색에서 모달 배경을 차단하지 못할 수 있다. 보조 설명이 제목 다음에 자동으로 읽힌다고 보장할 수 없다.
- **권장:** 열려 있는 동안 배경을 inert 처리하거나 검증된 모달 패턴을 사용하고, 설명이 있는 경우 `aria-describedby`로 연결한다. 키보드만 사용하는 경우, iOS VoiceOver, Android TalkBack에서 시트 열기→탐색→닫기→원래 버튼으로 복귀를 확인한다.

### P2 — 당겨서 새로고침의 진행·완료 상태를 표시할 것

- **상태:** 코드 반영 완료. 실제 iOS/Android 터치 동작은 실기기 검증이 필요하다.
- **근거:** 최초 검토 당시에는 제스처 피드백이 없었다. 현재 `lib/usePullToRefresh.ts`와 홈·기록·알림·마이페이지에서 임계값 안내, 실행 상태, 중복 방지, 중첩 스크롤 최상단 확인을 제공한다.

### P2 — 페이지별 로딩 스켈레톤의 보조기술 상태 전달을 통일할 것

- **상태:** 알림·기록·프로필 모두 코드 반영 완료. 각 기기 스크린리더 공지는 별도 확인이 필요하다.
- **근거:** 최초 검토 당시 일부 화면은 시각적 skeleton만 렌더링했다. 현재 로딩 영역은 `role="status"`와 숨김 문구를 제공하며 장식 블록은 숨긴다.
- **영향:** 화면 낭독기 사용자는 데이터가 로딩 중인지 바로 알지 못할 수 있고, 화면별 경험도 다르다.
- **권장:** 로딩 영역마다 적절한 `role="status"`와 간결한 숨김 안내를 제공하고, 완료 때 중복 낭독되지 않는지 확인한다. 장식용 skeleton 블록은 보조기술 트리에서 숨긴다.

### P2 — 알림의 읽음/안 읽음 상태를 시각 외의 방식으로 전달할 것

- **상태:** 코드 반영 완료. 알림 읽음 API의 운영 데이터 변경 테스트는 하지 않았다.
- **근거:** 현재 항목 이름·상태 텍스트·`aria-pressed`가 실제 `isRead` 값에 맞춰진다(`app/(main)/notifications/page.tsx`).
- **영향:** 읽은 항목이 흐리게 보이는 것 외에 상태 구분이 약할 수 있으며, 안 읽은 항목에 “읽음 처리”라고 읽어 주는 문구는 실제 상태와 혼동될 수 있다.
- **권장:** 읽음/안 읽음 상태를 텍스트 또는 적절한 접근성 상태로 노출하고, 읽은 항목의 이름은 현재 상태에 맞게 구성한다. 읽음 처리 성공/실패도 사용자에게 확인 가능하게 한다(현재 실패 시 `role="alert"` 오류는 제공됨: `:181`).

### P2 — 시트의 반열림 위치를 화면 높이에 따라 검증할 것

- **근거:** 시트의 반열림 애니메이션은 화면 크기와 무관한 `Math.min(halfY, 240)` 픽셀 이동을 사용한다(`components/ui/BottomSheet.tsx:41-45`). 시트 자체 높이는 최대 780px 및 뷰포트 비율로 제한한다(`:132`).
- **영향:** 작은 높이의 휴대폰이나 키보드가 올라온 상태에서 반열림 영역이 의도한 정보량을 보여 주지 않거나, 제목/액션이 가려질 가능성이 있다. 현재 코드만으로 실제 가림을 단정할 수는 없다.
- **권장:** 짧은 화면, 가로 방향, 화면 확대, 소프트 키보드 표시 상태에서 각 시트의 반열림·전체 열림·닫힘을 확인한다. 화면 높이에 따라 snap 지점을 계산하거나, 컨텐츠와 키보드에 맞춘 일관된 전체 열림 동작을 고려한다.

### P3 — 인증 화면의 작은 높이·키보드 표시 상태를 확인할 것

- **근거:** 로그인·가입 페이지는 `h-full`, 내부 `overflow-y-auto`, 상단 고정 여백과 `p-8`을 사용한다(`app/(auth)/login/page.tsx:70-71`, `app/(auth)/signup/page.tsx:64-66`).
- **영향:** 작은 화면에서 키보드가 나타날 때 현재 입력 필드와 제출 버튼이 스크롤 가능하고 가려지지 않는지가 중요하다. 소스만으로 키보드 리사이즈 정책이나 실제 포커스 스크롤을 확정할 수 없다.
- **권장:** iOS Safari/standalone 및 Android Chrome에서 로그인·가입 각 필드에 포커스하고, 비밀번호 표시 버튼·오류 메시지·제출 버튼에 접근할 수 있는지 테스트한다. 필요하면 작은 높이 구간에서 상단 간격과 세로 패딩을 줄인다.

### P3 — 오프라인 지원 범위를 화면에서 정확히 안내할 것

- **근거:** 서비스 워커는 오프라인 HTML을 설치 시 캐시하고(`public/sw.js:4-6`), 네트워크 탐색 실패 시 `/offline.html`을 보여 준다(`:24-27`). 버전이 붙은 Next 정적 자산과 공개 이미지를 캐시하지만(`:29-45`), API 응답이나 보호된 앱 화면 데이터 캐시는 확인되지 않는다. 오프라인 화면에는 다시 시도 버튼이 있다(`public/offline.html:3-5`).
- **영향:** 설치 가능한 PWA와 일부 캐싱은 제공되지만, 네트워크가 끊긴 상태에서 로그인 후 데이터를 계속 사용하거나 기존 식물 데이터를 탐색할 수 있다고 기대해서는 안 된다.
- **권장:** 오프라인 복구와 데이터 오프라인 사용을 제품 설명에서 구분한다. 실제 네트워크 차단 시 이미 열린 화면, 새로고침, 앱 재실행, 캐시 갱신 경로를 테스트하고, 지원하지 않는 기능은 명시적으로 안내한다.

## 제안 실행 순서

1. **안전 영역:** iOS Safari 및 standalone에서 상태 표시줄·하단 홈 인디케이터와 헤더/내비게이션의 간격을 확인하고 공통 safe-area 정책을 확정한다.
2. **접근성 핵심 흐름:** 비활성 하단 메뉴와 모달 배경 차단/설명 연결을 보완한 뒤 키보드·VoiceOver·TalkBack 흐름을 검증한다.
3. **피드백 일관성:** pull-to-refresh·주요 스켈레톤·알림 읽음 상태 피드백을 코드에 반영했다. 느린 네트워크/실기기에서 상태 길이와 낭독을 확인한다.
4. **기기 행렬 점검:** 작은 높이, 가로 화면, 큰 글자/화면 확대, 소프트 키보드, 오프라인, 느린 네트워크에서 홈·분양 시트·기록·알림·인증을 확인한다.

## 이번 리뷰에서 확인하지 않은 항목

- 색상 대비 수치, 터치 실측, 애니메이션 프레임/성능 및 실제 스크린리더 발화
- 실기기 브라우저별 주소창 동작, 안전 영역, 소프트 키보드와 시트의 상호작용
- 실계정의 프로필·비밀번호 저장, 알림 읽음, 이벤트 저장/업로드와 같이 운영 DB를 변경하는 사용자 여정

위 항목은 브라우저 코드 검증만으로 대체할 수 없으므로, 실기기 접근성·모바일 출시 검증 단계에서 별도로 확인하는 것을 권한다.
